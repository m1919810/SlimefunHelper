# Minecraft 1.21.11 铁砧附魔开销与规划

本仓库的自动附魔只允许两种操作：

1. 一个目标物品与一本附魔书合并；
2. 两本附魔书合并为一本中间附魔书。

不会把两个武器、两个工具或两个装备合并。这样既符合自动附魔的输入要求，也能把“先合并附魔书，再把书应用到工具”的路径纳入搜索。

## 原版 `AnvilScreenHandler.updateResult`

原版铁砧使用 0、1、2 三个槽位：0 是左侧物品，1 是右侧物品或附魔书，2 是输出。服务端根据这两个输入重新计算输出和等级价格；客户端的 `getLevelCost()` 是服务端同步后的本次价格，因此自动化点击输出时应以它为准。

附魔处理的大致顺序如下：

1. 初始等级价格包含两件输入物品的 `REPAIR_COST`（此前工作惩罚）。
2. 遍历右侧物品的附魔或附魔书的存储附魔。
3. 相同附魔且等级相同，等级加一；否则取两者较大等级，并限制在该附魔的最大等级。
4. 不同附魔必须通过 `Enchantment.canBeCombined` 兼容检查；每个冲突增加 1 级价格。目标物品是否适用由 `Enchantment.isAcceptableItem` 判断；附魔书之间合并时，附魔书本身允许作为承载物。
5. 每个成功应用的附魔增加 `Enchantment.getAnvilCost() * 结果等级`，即使已有等级没有提升也会收费。右侧是附魔书时，附魔部分会按原版规则折半，但至少为 1。
6. 输出的 `REPAIR_COST` 为：

   ```text
   min(max(leftRepairCost, rightRepairCost) * 2 + 1, Integer.MAX_VALUE)
   ```

   因此中间附魔书不能只记录“有哪些附魔”，还必须保留此前工作惩罚。

生存模式下价格达到 40 级时，原版会显示“过于昂贵”并阻止取出；创造模式绕过这一限制。自动附魔还会在点击前检查 `experienceLevel >= getLevelCost()`，不会因为客户端预测错误而强取输出。

## 为什么不能使用贪心策略

每次选择当前价格最低的附魔书并不一定得到全局最优结果。某些书先合并会产生较低的附魔书中间产物，另一些顺序会更早提高 `REPAIR_COST`，导致后续每一步都更贵。`AutoEnchantPlanner` 对书书合并和书上目标两类边都进行搜索；为控制搜索规模，每次只考虑物品栏中前 12 本含有目标附魔的书，因此最优性仅针对这 12 本书成立。

搜索过程中目标始终只有一个；书书合并只消耗两本书并产生一本新书，不会产生第二个工具目标。

## 经验等级不是线性经验值

铁砧扣除的是“等级”，不是固定数量的原始经验点。当前等级的累计经验阈值为：

```text
0..16:  level^2 + 6*level
17..31: floor(2.5*level^2 - 40.5*level + 360)
32+:    floor(4.5*level^2 - 162.5*level + 2220)
```

因此：

- 经验充足时，应优先使用总等级价格最小的路径，并比较每一步产生的 `REPAIR_COST`；
- 经验不足时，不能把原始经验点简单除以价格。每一步都必须重新检查当前整数等级是否至少为服务端价格；不可支付时停止；
- 由于等级阈值是非线性的，若以后扩展为离线批量规划，应以“每一步扣除等级后的累计经验差”作为原始经验消耗，而不是把各步价格相加后当作线性经验值。

当前模块采用分层策略：优先选择当前等级足以完成的路径，并在这些路径中选择总等级价格最低的；若都无法完成，则优先选择当前可连续执行步骤更多的路径，再比较第一步价格与总价。执行器随后每一步重新读取服务端价格和当前等级，因此扣除等级后会重新规划。
